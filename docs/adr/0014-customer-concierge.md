# Customer discovery, booking assistant and appointment changes

Customers start with nearby hubs (20 km straight-line radius), see each hub's actual complimentary options, and choose a hub before using manual booking or a natural-language assistant. Express servicing remains mandatory; at most one complimentary barber, massage or workspace option fits inside the service hour.

OpenRouter is an outbound adapter behind the booking assistant. A bounded tool loop can search real slots, read the authenticated customer's upcoming appointments, and prepare a booking/change proposal. It cannot execute arbitrary HTTP/SQL, choose a customer identity, charge a card, or confirm a payment. The customer confirms a stored, expiring proposal in the app; execution uses existing booking/resource/parts transactions. A held slot is displayed as awaiting payment, never as confirmed. Yoco remains the payment boundary.

The API derives customer identity from authenticated Cognito claims (a fixed configured demo customer only when security is disabled). Customer hub selection is limited to published service hubs, not operator membership claims. Private appointment and chat responses use no-store. Chat is bounded, not logged, and passed to OpenRouter only when configured; location is used only by discovery, not sent to the model. The app requests foreground location on user action and supports a clearly labelled demo location when permission is unavailable.

Confirmed appointments can change date/time and the free option until and including 48 hours before the original start. The replacement must also be at least 48 hours away. Changes lock the appointment, check an optimistic revision, replace resource allocations atomically, retain payment/parts associations, and append an outbox event. A failed allocation rolls back to the original appointment. Command receipts make retries safe even across the cutoff.

Failure controls: provider calls have connect/read timeouts, concurrency and token/tool budgets, with no automatic retry of mutations. Missing configuration/provider errors leave manual booking available. Stale revisions and occupied resources return conflicts; a missed cutoff never relies on the phone clock. Public directory queries validate coordinates, filter published hubs and cap results. Daily slot searches are bounded by hub opening hours and a 90-day booking horizon.

Rollout is additive (hub directory fields, appointment revision/receipts, assistant proposals). OpenRouter is disabled by a blank key/model and can be disabled independently. Roll back the application without removing additive tables/columns. Configure real hub coordinates/opening hours before launch; sample locations are explicitly demo data. Native platform location permissions must be registered when the Flutter platform shells are generated.
