# Hub capacity and trading hours

The hub owns its bookable physical resources and weekly trading schedule. Operators may edit a hub only after both their role and authenticated hub membership are verified. The path selects among authorized hubs; it does not grant membership.

A versioned PUT replaces capacities and seven trading days atomically. Repeating the same desired configuration returns the existing revision without another event. A stale revision with different content returns 409. Counts are simultaneous capacity (1–100 express bays, 0–50 barber chairs, massage rooms and workspaces). Zero hides that complimentary option from customer discovery. Open days must fit the mandatory 60-minute service; overnight/split shifts and date exceptions are deferred.

Settings take an exclusive hub row lock; every allocation path takes a shared hub lock until its transaction commits. The shared lock permits concurrent bookings while preventing settings from invalidating an allocation in flight. Existing active allocations protect their resources from retirement and prevent incompatible hours. Rows are deactivated and reused, never deleted. Reducing counts can require moving bookings first; automatic reassignment would hide an operational decision.

V16 adds a revision and weekly trading table and backfills existing daily hours. Newly provisioned hubs fall back to legacy hours until their seven-day configuration is saved. Changes and a HubSettingsChanged outbox event commit together. The transaction has a ten-second timeout; clients use a fifteen-second deadline and retain unsaved values on error. No third-party dependency is added.

Roll out all backend instances before allowing schedule edits; old versions do not enforce weekly hours. Roll back the UI independently; once hours have been edited, retain the new backend or restore legacy-compatible schedules before backend rollback. Do not drop V16 during rollback. Monitor HTTP endpoint duration/status (http.server.requests) and serv60.hub.settings.saves. Assumed initial alerts: settings 5xx above 1% over 5 minutes or p99 above 2 seconds for 10 minutes; thresholds require tuning and are not deployed alarms. Inspect database lock waits for timeout errors; refresh for revision conflicts; move affected bookings for capacity/hour conflicts. Never bypass the allocation guard by updating resource rows manually.
